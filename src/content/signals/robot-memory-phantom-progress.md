## 等待进入记忆以后

作者在 RoboMME 仿真的 PickXtimes 任务中，对已发布的 FrameSamp-Modul 策略插入两次五秒暂停。50 个配对测试回合里，成功数从 47 降到 16；相同暂停若不进入记忆、也不推进其时间戳，成功数为 45。作者将提前停止的现象称为“虚假进展”。[论文 §3–4、Table 1](https://arxiv.org/html/2611.14488v1#S3)

## 阅读批注 · 验收里加一种“什么也没完成”的情况

这项实验给能力评估提供了一个具体追问：任务节奏变化以后，系统还会正确判断完成条件吗？可以在常规任务之外加入等待确认、短暂停顿、动作重试等对照，保持目标与已完成工作不变，只改变中间耗时。验收记录应同时保留实际完成次数、提前结束次数和恢复后的额外动作。

把这个问题迁移到业务 Agent 时，可以构造另一种测试：接口已经返回“受理”，但业务处理尚未完成。随后延迟回执或重复通知，观察助手是否仅凭等待时长、对话轮数就宣告成功。这里需要对照可查询的业务结果，并用请求编号区分同一动作的多次通知。这是借鉴实验设计提出的检查，论文没有测试这类业务系统。

产品侧还可以检查“处理中”和“已完成”分别由什么证据触发。若最终结果只能由外部系统确认，就应保留对应回执。评估成本时，把误报完成后产生的人工核对与补偿处理一并计算，才能看见正常成功率之外的使用负担。

## 阅读边界

这是预印本中的脚本化仿真实验，不能推出真实机器人或所有 Agent 都会同样失败。作者的事件索引也会误删真实重复动作；时长本身属于任务要求时仍需保留时钟。上述业务对照尚未实测。[论文 §6–7](https://arxiv.org/html/2611.14488v1#S6)
